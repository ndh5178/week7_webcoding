## 공부 순서

### STEP 1. 사전 지식 — 왜 트리 인덱스가 필요한가?

코드를 보기 전에 이 개념들을 먼저 이해하자.

**선형 탐색의 한계** (`src/linear/linear_search.c` 참고)
- 100만 건의 데이터에서 선형 탐색은 최악 O(N) = 100만 번 비교
- B 트리/B+ 트리는 O(log N) ≈ 20번으로 해결

**이진 탐색 트리(BST)의 한계**
- BST는 데이터가 편향(정렬된 순서로 삽입)되면 O(N)으로 퇴화
- 트리 높이를 항상 낮게 유지해야 함 → B 트리 등장

**B 트리의 핵심 아이디어**
- 하나의 노드에 여러 개의 키를 저장 (BT_ORDER = 32개)
- 항상 균형을 유지 (모든 리프가 같은 깊이)
- 디스크 I/O 최소화 목적으로 설계 (노드 = 디스크 블록 하나)

### STEP 2. 자료구조 이해 — 헤더 파일 읽기

#### 2-1. B 트리 구조체 (`btree.h`)

```
BTNode 하나의 구조:
┌────────────────────────────────────────────────────┐
│  keys:      [10] [20] [30] ...  (정렬된 키)          │
│  ptrs:      [p0] [p1] [p2] ...  (각 키의 레코드 ptr) │
│  children:  [c0] [c1] [c2] [c3] (자식 노드 ptr)     │
│  num_keys:  현재 키 개수                             │
│  is_leaf:   0=내부 노드, 1=리프 노드                 │
└────────────────────────────────────────────────────┘

children[i]에는 keys[i-1] < k < keys[i] 범위의 키만 있다.
→ B 트리는 내부 노드와 리프 구조가 동일 (ptrs 포함)
```

#### 2-2. B+ 트리 구조체 (`bplus_tree.h`)

```
BPNode (내부 노드 / 리프 래퍼):
┌─────────────────────────────────────────────┐
│  keys:      탐색 경로용 키 (레코드 없음!)      │
│  children:  자식 BPNode 배열                 │
│  is_leaf:   0=내부, 1=리프                   │
│  leaf:      is_leaf==1일 때 BPLeaf 접근용     │
└─────────────────────────────────────────────┘

BPLeaf (실제 데이터 보관):
┌──────────────────────────────────────────────┐
│  keys:  정렬된 키 배열                         │
│  ptrs:  레코드 포인터 (실제 데이터!)            │
│  next:  다음 BPLeaf 포인터 ← 범위 탐색의 핵심  │
└──────────────────────────────────────────────┘

리프 연결 리스트: [10,20] → [30,40] → [50,60] → NULL
```

**체크포인트**: BPNode와 BPLeaf가 왜 분리되어 있는지 설명할 수 있어야 한다.

### STEP 3. 삽입 로직 — `insert_rec()` 함수

두 파일 모두 재귀 삽입을 사용한다. 비교하며 읽자.

#### 공통 흐름

```
insert_rec(node, key, record_ptr, &split)
    ↓
  리프 노드? ──Yes──→ 해당 위치에 삽입 (memmove 사용)
    ↓ No                ↓
  자식으로 재귀          num_keys == BP_ORDER?
    ↓                   ├─ Yes → split 호출 → return 1
  자식이 분할됨?         └─ No  → return 0
    ↓ Yes
  승격 키를 현재 노드에 삽입
    ↓
  현재 노드도 꽉 참? → split → return 1
```

#### 핵심: memmove 이해하기

```c
// 삽입 위치 pos 이후 원소들을 오른쪽으로 한 칸씩 이동
memmove(&keys[pos + 1], &keys[pos], sizeof(int) * (num_keys - pos));
```

예시: `keys = [10, 30, 40]`, `pos = 1`, 삽입할 key = 20
```
memmove 전: [10, 30, 40, ?]
memmove 후: [10, 30, 30, 40]  ← 30부터 오른쪽으로 복사
삽입 후:    [10, 20, 30, 40]
```

**체크포인트**: `memmove`와 `memcpy`의 차이를 알아야 한다.
(힌트: 메모리 영역이 겹칠 때 `memcpy`는 위험할 수 있다)

### STEP 4. 분할 로직 — B 트리 vs B+ 트리의 결정적 차이

#### B 트리: move-up (`split_node`)

```
꽉 찬 노드: [10, 20, 30, 40]  (BT_ORDER=4, mid=2)
               ↓ split
왼쪽: [10, 20]   승격: 30   오른쪽: [40]
      ↑ 왼쪽에서 제거    ↑ 오른쪽에서도 제거!
```

#### B+ 트리: copy-up (`split_leaf`) — 리프 분할에만 적용

```
꽉 찬 리프: [10, 20, 30, 40]  (BP_ORDER=4, mid=2)
               ↓ split
왼쪽 리프: [10, 20]   승격(복사): 30   오른쪽 리프: [30, 40]
                                          ↑ 오른쪽에 30이 남아 있음!
```

#### 왜 차이가 있는가?

| | B 트리 | B+ 트리 리프 |
|---|---|---|
| 방식 | move-up | copy-up |
| 이유 | 내부 노드도 레코드 보유 가능 | 리프에서 키를 제거하면 해당 레코드에 접근 불가 |
| 결과 | 승격 키는 양쪽 노드에서 제거 | 승격 키는 오른쪽 리프에 그대로 유지 |

**체크포인트**: B+ 트리 내부 노드 분할(`split_internal`)은 move-up을 사용한다. 왜?

### STEP 5. 탐색 로직 비교

#### B 트리 탐색 (`btree_search`)

```
루트
 │
 ├─ 키 비교 (내부 노드)
 │   ↓ 발견하면 즉시 반환! ← B 트리의 특징
 ├─ 자식으로 이동
 │   ...
 └─ 리프까지 내려가도 없으면 NULL
```

#### B+ 트리 탐색 (`bptree_search`)

```
루트
 │
 ├─ 키 비교 (내부 노드) ─ 레코드 없음, 방향만 결정
 ├─ 자식으로 이동
 │   ...
 └─ 반드시 리프까지 내려감 → BPLeaf에서 검색
```

**체크포인트**: B 트리는 운이 좋으면 루트에서 바로 찾을 수 있다. B+ 트리는 항상 리프까지 간다. 어느 쪽이 더 유리한가?

### STEP 6. 범위 탐색 비교 — B+ 트리의 최대 장점

#### B 트리 범위 탐색 (`range_rec`)

전체 트리를 재귀 순회해야 한다.

```
range_rec(root, lo=25, hi=45)
├─ range_rec(children[0], ...)  ← 재귀
│   └─ ...
├─ keys[0]=20 → 범위 밖 (스킵)
├─ range_rec(children[1], ...)  ← 재귀
│   └─ keys=[25,30,35] → count=3
├─ keys[1]=40 → count++
└─ range_rec(children[2], ...)  ← 재귀
    └─ ...
시간 복잡도: O(N) 최악의 경우
```

#### B+ 트리 범위 탐색 (`bptree_range`)

리프 연결 리스트를 순차 스캔한다.

```
1. lo=25에 해당하는 리프까지 O(log N)으로 이동
2. 리프 연결 리스트를 따라 O(k)로 스캔
   [20,25] → count++ (25>=lo)
   [30,40] → count++, count++
   [50,60] → 50>hi → return
시간 복잡도: O(log N + k)
```

**체크포인트**: 실제 벤치마크 결과(`web/assets/results.json`)에서 이 차이가 숫자로 나타나는지 확인해보자.

### STEP 7. 메모리 해제 — 후위 순회

```c
static void free_node(BTNode *node) {
    if (node == NULL) return;
    if (!node->is_leaf) {
        for (int i = 0; i <= node->num_keys; i++)
            free_node(node->children[i]);  // 자식 먼저 해제
    }
    free(node);  // 그 다음 자신 해제
}
```

자식을 먼저 해제하지 않으면 자식 포인터가 사라져 메모리 누수 발생!

## 핵심 개념 정리표

| | B 트리 | B+ 트리 |
|---|---|---|
| 레코드 위치 | 내부 노드 + 리프 | 리프만 |
| 탐색 경로 | 불균일 (운 좋으면 일찍 발견) | 항상 리프까지 (일정한 깊이) |
| 리프 연결 | 없음 | next 포인터로 연결 리스트 |
| 분할 방식 | move-up | 리프: copy-up, 내부: move-up |
| 범위 탐색 | 전체 트리 순회 O(N) | 연결 리스트 스캔 O(log N + k) |
| 실제 사용처 | 일반 파일 시스템 | DB 인덱스 (MySQL InnoDB 등) |

## 자주 헷갈리는 포인트

**Q1. BPNode와 BPLeaf를 왜 따로 만들었나?**
BPNode는 트리 구조(부모-자식 관계)를 담당하고, BPLeaf는 데이터 + 연결 리스트를 담당한다. 둘을 분리해야 리프 연결 리스트를 만들 수 있다.

**Q2. `key >= keys[i]`로 탐색 방향을 결정하는 이유?**
B+ 트리 내부 노드에서 `keys[i]`는 `children[i+1]`의 최솟값이다. 따라서 `key >= keys[i]`이면 오른쪽 자식으로 가야 한다.

**Q3. copy-up 후 오른쪽 리프에 키가 중복 보이는 것이 정상인가?**
정상이다. 내부 노드의 키는 탐색 경로만 제공하므로, 오른쪽 리프의 첫 키와 부모의 키가 같아도 된다. 실제 데이터(레코드)는 리프에만 존재한다.

**Q4. `memmove` vs `memcpy` 언제 써야 하나?**
src와 dst 메모리 영역이 겹칠 때는 반드시 `memmove`를 써야 한다. 배열 내부에서 원소를 이동할 때는 항상 겹치므로 `memmove`가 맞다.
